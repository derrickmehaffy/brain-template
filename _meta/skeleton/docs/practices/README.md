# Practices

One file per fact this brain has already worked out: what it is, how well it is known, and when it
was last checked. Look a fact up before you re-derive it:

```bash
_meta/brain practices search <terms>
```

Add or change an entry through the `brain-write-practice` skill. `INDEX.md` is generated by
`_meta/brain practices index`; never edit it by hand. `_meta/brain practices lint` holds every entry
to the schema below.

## Schema

One file per fact, named `<id>.md`:

```yaml
---
id: kebab-case-id            # must equal the filename
tags: [a, b]                 # non-empty
durability: durable | volatile
evidence: researched | reproduced | reliable
verified: YYYY-MM-DD
source: <free text: commit, issue URL, forum post, log path>; 2+ entries (comma-separated) for reliable
recheck: <command or URL>    # required when volatile
reproduced-by: <how>, YYYY-MM-DD   # required at reproduced and reliable
reviewed-against: [ids]      # required; [] means nothing was close
superseded-by: <id>          # optional; written on the old entry when a newer one replaces it
---
```

- `durability`: `volatile` means the fact can change under you (a version, a setting, an
  endpoint); it needs a `recheck` that anyone can run. `durable` means it will hold until the
  system is redesigned.
- `evidence` is how well the fact is known, not how important it is:
  - `researched`: read from source, docs or a statement; nobody watched it happen. **Reading code
    is `researched`.**
  - `reproduced`: observed running.
  - `reliable`: held across two or more occasions. It needs two or more `source` entries.
- `verified` is the last day someone confirmed the fact. An entry not verified within
  `practices.stale_after_days` (default 180, set in `brain.json`) is reported as stale. Re-check
  it, then update the date.
- `reviewed-against` lists the existing entries you compared this one with before writing it
  (`_meta/brain practices candidates` ranks them); `[]` means nothing was close.
- `superseded-by` is how an entry is retired. Supersede, never delete: keep the old file, point it
  at its replacement, and it stops being reported as stale.

## Body

After the frontmatter: the point in one or two lines (the index shows its first sentence), then the
specifics, then what it means for the work. Link another entry with `[[id]]`; every link must
resolve to an entry.

## Commands

| Command | What it does |
| --- | --- |
| `_meta/brain practices lint` | Check every entry. Errors block (exit 1); stale entries warn. |
| `_meta/brain practices index [--check]` | Write `INDEX.md`; with `--check`, fail when it is out of date. |
| `_meta/brain practices candidates (FILE \| --tags A,B --text T)` | Rank existing entries that may duplicate a proposed one. |
| `_meta/brain practices search TERM...` | Entries matching every term. A `volatile` hit is printed with its `recheck`: run it first. |

## Example

```markdown
---
id: resolver-negative-cache-ttl
tags: [dns, caching]
durability: volatile
evidence: reproduced
verified: 2026-11-02
source: resolver manual, section on negative caching
recheck: dig +noall +authority nonexistent.example.com
reproduced-by: queried the resolver twice and watched the answer's TTL count down, 2026-11-02
reviewed-against: []
---
The resolver caches "no such name" answers for the zone's negative TTL, not for the record TTL.

A record added after a failed lookup can look missing for up to that long. After adding a record,
wait out the negative TTL or flush the resolver's cache before concluding the record is broken.
```
